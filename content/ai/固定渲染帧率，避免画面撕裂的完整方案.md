# 固定渲染帧率，避免画面撕裂的完整方案

先点明核心：**画面撕裂的本质 = 后台渲染完成、Swap 交换缓冲区的时机，和显示器硬件刷新不同步**。
 固定帧率（比如锁死严格 60 帧，刚好等于显示器刷新率）只是前提，必须配合**双缓冲 / 多缓冲 + VSync + 时序对齐**组合方案，才能彻底防撕裂，下面分原理、方案、代码实现、坑点讲清楚。

## 前置基础知识

1. 显示器硬件刷新是固定周期（60Hz=16.666ms），屏幕只会在 ** 垂直消隐期（VBlank）** 完成新旧画面切换。
2. 单缓冲：一边画一边显示，必然撕裂，现代游戏早已淘汰。
3. 双缓冲（前台缓冲：当前屏幕画面 / 后台缓冲：正在绘制的新画面），只有 Swap 交换两个缓冲区时画面才会更新。 撕裂只会发生在：**非 VBlank 时间段执行 Swap**。

固定渲染帧率想要防撕裂，一共 4 套方案，从易到难。

## 方案 1：固定帧率 = 显示器刷新率 + 开启 VSync（最简单通用）

### 原理

把你的**固定渲染帧率严格等于显示器刷新率**（60Hz 屏固定 60 帧、144Hz 屏固定 144 帧），同时开启 VSync。

1. 代码固定循环帧率和屏幕刷新率完全匹配；
2. VSync 强制`SwapBuffers`交换缓冲区**只能在显示器 VBlank 垂直消隐期执行**；
3. 渲染永远刚好在下一次刷新前完成，交换时机完全对齐硬件刷新，从根源杜绝撕裂。

### 适配场景

单机小游戏、RPG、剧情游戏，能接受 VSync 带来的小幅输入延迟。

### 关键要求

固定帧率必须**完全等于屏幕原生刷新率**，不能 60 帧跑在 144Hz 屏幕上，帧率和刷新率不匹配，VSync 会强制降频，反而卡顿。

### 框架代码示例

#### Raylib

```cpp
InitWindow(800,600,"Fixed 60FPS");
SetTargetFPS(60); // 固定渲染帧率=屏幕60Hz刷新率
SetWindowState(FLAG_VSYNC_HINT); // 开启VSync
```

#### SFML

```cpp
window.setFramerateLimit(60);    // 固定帧率
window.setVerticalSyncEnabled(true);
```

#### GLFW 原生

```cpp
glfwSwapInterval(1); // 开启VSync，1=同步刷新率，0=关闭
```

`glfwSwapInterval(n)`规则：

- 1：每次屏幕刷新交换一帧，匹配 60Hz=60 帧
- 2：每两次刷新交换一帧，60Hz=30 帧

## 方案 2：固定帧率 + 精准时序对齐（不开 VSync，低延迟防撕裂）

竞技游戏不想开 VSync 加延迟，**手动把固定帧的结束时间，精准卡进显示器 VBlank 窗口**，软件层面对齐刷新时机。

### 实现思路

1. 用高精度时钟读取显示器刷新周期，算出每一次 VBlank 的时间点；
2. 固定渲染帧的计算、绘制逻辑提前完成；
3. 用高精度休眠，精准等待到 VBlank 时间段，立刻执行 SwapBuffers。

### 难点

1. Windows 普通`Sleep`精度只有 1ms，达不到微秒级时序，必须使用**高精度定时器 (QueryPerformanceCounter)**；
2. 不同显示器、显卡、桌面环境的 VBlank 时间窗口不一样，兼容性极差；

### 结论

普通开发者几乎不用，只有专业引擎底层、电竞游戏才会自研时序对齐，新手不推荐。

## 方案 3：固定帧率 + 多缓冲（三缓冲）优化 VSync 延迟

开启 VSync 固定帧率容易堆积一帧延迟，开启三缓冲可以缓解，依旧保证不撕裂：

1. 双缓冲只有前后两块画布，渲染完必须等刷新；
2. 三缓冲增加一个预备缓冲，GPU 可以提前渲染下一帧放入预备队列；
3. VSync 触发交换时，直接拿预备好的画面，减少空闲等待时间，撕裂依旧不存在，输入延迟明显降低。

大部分显卡控制面板、引擎会自动开启三缓冲，无需手写代码。

## 方案 4：硬件层面：G-Sync (英伟达) / FreeSync (AMD) 自适应同步

就算你的程序是**固定帧率**，搭配 VRR 可变刷新率显示器，可以完美解决两大痛点：

1. 关闭传统 VSync，没有强制等待，输入延迟低；
2. 显示器主动适配显卡的帧完成时间，显卡画完画面，显示器立刻刷新，永远不会撕裂；
3. 哪怕你的固定帧率小幅波动（比如固定 60 帧偶尔掉到 58 帧），自适应同步依旧生效。

这是目前高端 PC 最优解，软件固定帧率 + 硬件自适应同步，兼顾低延迟 + 无撕裂。

## 固定帧率防撕裂的致命误区（高频踩坑）

### 误区 1：只要固定帧率，就能自动不撕裂

错误。固定帧率只是循环速度固定，**Swap 交换时机依然随时可能落在显示器刷新中途**，照样撕裂。
 例：144Hz 显示器强行固定 60 帧且关闭 VSync，撕裂非常明显。

### 误区 2：固定帧率低于刷新率，VSync 会自动降帧

60Hz 屏幕固定 30 帧 + VSync，`glfwSwapInterval(2)`，显示器每两次刷新才换一次画面，依旧不会撕裂，画面会小幅卡顿。

### 误区 3：固定帧率高于屏幕刷新率

比如 60Hz 屏硬固定 120 帧，就算开 VSync，也只能锁在 60 帧运行，多余帧会被丢弃。

## 不同场景最终选型方案

1. **休闲单机（首选）** 固定帧率 = 显示器刷新率 + 开启 VSync，简单稳定，完美防撕裂。
2. **竞技游戏（FPS/MOBA）** 方案 A：固定帧率上限高于刷新率 + 开启 G-Sync/FreeSync 自适应同步，关闭 VSync，低延迟无撕裂； 方案 B：无自适应显示器，关闭 VSync，轻微撕裂换取最低延迟。
3. **手游固定帧率（30/60/120 帧档位）** 手机系统自带 VSync 同步机制，设置固定帧率档位后，系统底层自动对齐屏幕刷新率，开发者无需额外处理撕裂。

## 补充：和之前可变渲染架构的联动

我们游戏架构是**逻辑固定步、渲染可变**，所谓的「固定渲染帧率」只是**设置渲染帧率上限封顶**，并不是老式死循环固定休眠的老旧帧循环：

1. 渲染上限锁定等于屏幕刷新率 + VSync，画面无撕裂；
2. 底层 deltaTime 依旧正常计算，alpha 插值照常工作；
3. 逻辑 FixedUpdate 完全不受渲染帧率限制，物理、碰撞稳定不变。
