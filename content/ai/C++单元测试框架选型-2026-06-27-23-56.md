当然可以！**Google Test 和 doctest 完全可以在同一个自研引擎项目中共存**，而且这恰恰是我推荐的分层策略的核心优势。

它们不是竞争关系，而是互补关系——就像你在工具箱里同时放着锤子和螺丝刀，根据需要选用就好。

---

### ✅ 为什么它们能和平共处？

1. **它们是独立的静态库/头文件库**：两者都只包含头文件（或编译成独立的静态库），没有全局状态的冲突。只要不在同一个 `.cpp` 文件中同时 `#include` 两个框架的冲突宏（比如都定义了 `TEST`），就不会有问题。
2. **测试可执行文件是分离的**：通常你会为不同模块创建独立的测试可执行文件。比如：
   - `MathTests.exe` → 使用 doctest，编译极快
   - `CoreTests.exe` → 使用 GTest + GMock，功能完整
   - `RenderTests.exe` → 使用自研框架
   它们各自运行，互不干扰。
3. **构建系统的灵活性**：CMake 等构建工具可以轻松控制不同目标链接不同框架。你甚至可以在同一个解决方案中同时包含两者。

### 🛠️ CMake 配置示例

```cmake
# 引入 doctest（单头文件方式）
add_library(doctest INTERFACE)
target_include_directories(doctest INTERFACE third_party/doctest)

# 引入 Google Test（从源码或系统包）
find_package(GTest REQUIRED)
include_directories(${GTEST_INCLUDE_DIRS})

# 数学库测试（使用 doctest）
add_executable(MathTests Math/Tests/MathTests.cpp)
target_link_libraries(MathTests EngineMath doctest)

# 核心系统测试（使用 GTest）
add_executable(CoreTests 
    Core/Tests/ResourceManagerTest.cpp
    Core/Tests/SceneGraphTest.cpp
)
target_link_libraries(CoreTests EngineCore ${GTEST_LIBRARIES} ${GMOCK_LIBRARIES})
```

### ⚠️ 唯一的注意事项：宏命名冲突

如果你的某个测试文件不小心同时包含了两个框架的头文件，可能会因为都定义了 `TEST` 或 `CHECK` 这样的宏而导致编译错误。

**解决方案**：

- **分文件使用**：确保每个 `.cpp` 测试文件只包含一种框架（这是最安全的方式）。
- **如果必须混用**（极少情况），可以这样处理：
  ```cpp
  // 先包含 doctest，并重命名其宏
  #define DOCTEST_CONFIG_IMPLEMENT
  #include <doctest.h>
  #define DOCTEST_CHECK CHECK  // 如果需要别名
  #undef TEST  // 清除可能冲突的宏
  // 再包含 GTest（但建议不要这么做）
  #include <gtest/gtest.h>
  ```

但我强烈建议**不要在同一文件中混用**，这会增加维护复杂度，且没有实际收益。

   ```bash
   ./MathTests.exe && ./CoreTests.exe && ./RenderTests.exe
   ```

### 💡 实践建议

如果你刚开始搭建引擎，可以这样分步走：

1. **先用 doctest 搞定数学库**，让它先跑起来，快速验证底层逻辑。
2. **引入 GTest**，为核心系统（资源、场景、任务调度）补上单元测试。
3. **统一 CI 脚本**，让所有测试一起运行，但独立报告结果。

这样既享受了 doctest 的编译速度（数学库迭代频繁），又拥有了 GTest 的强大能力（复杂系统测试），两全其美。
