# 结论前置

玩家**原始输入读取放在可变的渲染主循环（每渲染帧必读）**，但**输入的响应逻辑、移动执行、判定，必须放进固定 FixedUpdate 逻辑步**。
 简单一句话：
**输入采样是可变帧（越快越灵敏），输入生效是固定步（逻辑统一稳定）。**

## 一、为什么输入读取要放在可变帧（每帧立刻读）

键盘、鼠标、手柄输入是操作系统实时事件，渲染循环帧率更高（144/240Hz），有两个核心好处：

1. **输入无延迟、手感灵敏** 如果强行等到 60Hz 固定逻辑步才读取输入，最坏会多等一整帧（16.67ms），高刷玩家会明显感觉操作拖沓、有延迟。 可变渲染帧每一帧都轮询输入状态，按下按键瞬间就能捕获。
2. 不会丢失瞬时按键 比如极快的轻点按键，刚好卡在两次固定逻辑帧中间，如果只在 FixedUpdate 读输入，很容易直接漏掉按键信号。

```cpp
// 可变主循环（每渲染帧执行）：只读输入状态，不写游戏逻辑
void ProcessInput()
{
    isKeyADown = IsKeyDown(KEY_A);
    mousePos = GetMousePosition();
    leftMouseDown = IsMousePressed(MOUSE_LEFT);
}
```

这里只是**记录按键状态**，不会直接修改角色位置、速度。

## 二、为什么输入执行逻辑，必须走固定 FixedUpdate

角色移动、跳跃、攻击、技能判定这些行为，属于**游戏核心逻辑**，必须服从固定时间步，原因：

1. **移动速度全局统一，所有设备手感一致** 固定 dt = 1/60s，每次移动计算公式完全相同，60 帧、144 帧电脑、手机运行，角色跑速完全一样。 如果在可变帧直接执行移动：帧率越高跑的越快，高刷屏天生占优势，联机彻底无法同步。

```cpp
// 固定逻辑步，统一执行输入结果
void FixedUpdate(float fixedDT)
{
    // 使用上一帧渲染循环采集到的按键状态
    if(isKeyADown)
        player.pos.x -= speed * fixedDT;
}
```

2. **碰撞、跳跃、攻击判定稳定**
   跳跃起跳、攻击命中、近战碰撞都绑定固定步，不会因为卡顿 dt 变大出现穿墙、判定失效。
3. 多人联机硬性要求
   服务端一律使用固定步运算，客户端输入只做上报，最终逻辑以固定步为准。如果客户端可变帧执行逻辑，客户端与服务端必然错位。

## 三、完整流程时序（标准游戏主循环）

```plaintext
1. 可变渲染帧开始，获取本帧 deltaTime，累加进时间累加器 accumulator
2. 【可变步】立刻读取键盘/鼠标输入，更新全局按键状态变量
3. 循环执行 FixedUpdate 固定逻辑步（直到 accumulator 不足一个fixedDT）
   └── 在FixedUpdate里，读取已经缓存好的按键状态，执行移动、技能、碰撞
4. 计算alpha插值系数，用前后两帧逻辑坐标做画面插值
5. 【可变步】渲染画面、播放动画
```

## 四、特殊输入场景细分

### 1. 长按持续移动（WASD 方向）

- 采样：可变帧实时刷新按下状态
- 执行：固定步匀速位移，标准方案。

### 2. 瞬时按键（跳跃、开枪、技能）

需要加**按键按下标记（瞬时 flag）**，而非单纯的长按状态：

1. 可变帧检测到按键刚按下，标记 `jumpTrigger = true`
2. FixedUpdate 执行时，判断 flag 执行跳跃，执行完毕立刻置 `false` 避免长按重复触发，同时保证触发逻辑在固定步。

### 3. 鼠标视角、镜头旋转

两种做法：

1. **逻辑绑定固定步（竞技网游）**：视角旋转角度在 FixedUpdate 计算，稳定同步。
2. **画面插值可变渲染（单机 3D）**：原始鼠标差值可变帧读取，旋转角度做平滑插值，画面更跟手，底层逻辑角度依然以固定步为准。

## 五、常见误区

### 误区 1：读取和执行都放 FixedUpdate

手感延迟，高刷设备优势完全浪费，操作发闷。

### 误区 2：读取执行全放可变渲染帧

帧率决定速度，卡顿瞬移，联机必崩，物理碰撞极易出 BUG。

## 六、精简总结

1. **输入采样（读按键）：可变渲染帧**，追求低延迟、不漏键、手感灵敏；
2. **输入逻辑执行（移速、判定、技能）：固定 Fixed 步**，保证运算稳定、速度统一、碰撞可靠、联机同步；
3. 两者配合，兼顾**操作手感**和**逻辑稳定性**，是行业通用的标准设计。
